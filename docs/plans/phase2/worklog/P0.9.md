## Scope delivered

### `src/db/schema.sql` — full current schema (fresh databases)

- `nodes`: `+ provenance TEXT DEFAULT 'tree-sitter'`, `+ scip_symbol TEXT`,
  `+ scip_index_path TEXT`, `+ stale INTEGER DEFAULT 0`, `+ staleness_visible INTEGER DEFAULT 0`.
- `edges`: `+ provenances TEXT`, `+ confidence REAL DEFAULT 0.7`, `+ subkind TEXT`,
  `+ stale INTEGER DEFAULT 0`, `+ staleness_visible INTEGER DEFAULT 0`.
- New indexes: `idx_nodes_provenance`, partial `idx_nodes_scip_symbol` /
  `idx_nodes_scip_index`, and the unique `idx_edges_dedup` on
  `(source, target, kind, COALESCE(subkind,''), COALESCE(line,-1), COALESCE(col,-1))`.
- New tables: `scip_documents`, `scip_ingestions`, `scip_external_refs` (the last with an
  `ON DELETE CASCADE` FK to `nodes`), plus their indexes.
- Header comment updated — schema.sql is the full current schema, version 5.

### `src/db/migrations.ts` — migration v5 + version bump

- `CURRENT_SCHEMA_VERSION` 4 -> 5.
- New migration entry `version: 5`: the `ALTER TABLE` / `CREATE INDEX` / `CREATE TABLE`
  DDL above. `edges.subkind` is added **before** the dedup step that `COALESCE`s it.
- Historical-edge de-dup: `DELETE FROM edges WHERE rowid NOT IN (SELECT MAX(rowid) ...
  GROUP BY <fingerprint>)` keeps the **newest** row per fingerprint (most likely to carry
  current provenance/metadata), then the unique index is created — it would throw if any
  duplicate survived.
- Emits the plan-mandated one-line note to **stderr** (safe for MCP stdio transports):
  "Existing edges retain their original provenances; run 'codegraph index' to upgrade
  incrementally." Per plan P0.9, `scope-resolved` is deliberately **not** back-filled onto
  historical `tree-sitter` edges.

## Interaction note

`idx_edges_dedup` is now a UNIQUE index, but the edge-writing path is still the legacy
`insertEdge` (`INSERT OR IGNORE`) until **P0.4** lands `upsertGraphEdge`. In this
intermediate state `INSERT OR IGNORE` silently drops a conflicting edge instead of merging
it — acceptable only because P0.4 follows immediately in this same execution. The
cross-extractor merge semantics are not correct until P0.4.
