# P2.3.1 — Broaden `supersedeTreeSitter` predicate

**Status**: complete
**Date**: 2026-05-24
**Decisions**: design doc Decision 1 (round 2 finding 2: shadow row cleanup must cover both `'tree-sitter'` and `'tree-sitter (scip-empty-fallback)'`).

## Changes (`src/extraction/scip/persister.ts`)

One-line predicate change in `supersedeTreeSitter` ([persister.ts:941](../../../src/extraction/scip/persister.ts#L941)):

```diff
- `SELECT id FROM nodes WHERE file_path = @p AND provenance = 'tree-sitter'`
+ `SELECT id FROM nodes WHERE file_path = @p AND provenance LIKE 'tree-sitter%'`
```

Same change in the node-DELETE statement immediately below.

## Why this is safe re: STAGE E's empty-fallback re-creation

`supersedeTreeSitter` runs **before** `maybeEmptyFallback` ([persister.ts:646](../../../src/extraction/scip/persister.ts#L646)) on the per-doc loop. The ordering:

```
for each SCIP doc:
  supersedeTreeSitter(doc.relativePath)  // wipes ALL tree-sitter% rows
  persistDocNodes(...)
  persistDocEdges(...)
  if doc.occurrenceCount === 0:
    maybeEmptyFallback(...)              // creates fresh fallback rows if needed
```

So the broader predicate wipes ANY tree-sitter row (shadow OR fallback) for this file, then STAGE E's fallback re-creation produces fresh rows when warranted. Net effect: empty docs that previously had fallback rows STILL have fresh fallback rows after re-ingest; they just go through a delete-and-rewrite cycle instead of an idempotent skip.

The pre-existing `scip-ingester.test.ts` `"is idempotent across re-ingestion of the committed index"` test specifically verifies this round-trip — it still passes.

## Consistency with P2.2

P2.2's `deleteFileTreeSitterRows` (sync-side shadow cleanup) uses the same `LIKE 'tree-sitter%'` predicate. With this P2.3.1 change, the SCIP-ingest path and the sync-shadow path now have **consistent semantics for "what counts as a tree-sitter row for this file"** — they delete the same set of rows.

## Risk callouts

- **Edge case: a `'tree-sitter'` row whose file_path happens to match a SCIP doc's relativePath** — this is the exact case `supersedeTreeSitter` is FOR. The broader predicate doesn't change that semantic; it just adds the fallback variant to the set being cleared.
- **No new SQL site** in the inventory. The same prepared statement is re-issued with a wider WHERE clause — the CI bypass guard doesn't flag this because the DELETE is part of a write statement (correctly skipped via `isPartOfWrite`).
- **`provenance LIKE 'tree-sitter%'`** could theoretically match a future provenance like `'tree-sitter-experimental'`. If such a value is added to `GraphProvenance`, this predicate would silently delete those rows during SCIP ingest. Mitigation: review this predicate when adding any new `tree-sitter*` provenance. Same mitigation note in P2.2.2's worklog.
