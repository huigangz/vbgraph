## Classification: PUBLIC vs INTERNAL vs ONE-SHOT

- **PUBLIC** — reachable from the `CodeGraph` API surface, MCP tools, CLI commands. MUST apply `freshPredicate()` (Decision 4). Edge queries additionally apply `visibleNodeIdPredicate()` (Decision 7). Adds an `*IncludingStale` / `*IncludingDanglingEndpoints` sibling when an internal caller needs raw access.
- **INTERNAL** — only invoked from inside QueryBuilder for write-path bookkeeping (SCIP STAGE B cleanup, edge upsert lookup, STAGE 0 audit). Does NOT apply the filter — these helpers manage stale rows by direct manipulation. They MUST be on the explicit `*IncludingStale` whitelist for the CI guard.
- **ONE-SHOT** — runs once during a schema migration. Pre-dates any stale-marking. No filter, no whitelist needed (the migration completes before stale columns are populated).

## Lessons (post-P2.1.5 / P2.1.8)

- **The initial grep `SELECT.*FROM\s+(nodes|edges)` missed several site categories**:
  1. **`JOIN nodes`** targets (multi-table SELECT) — e.g. `FROM nodes_fts JOIN nodes ON …`. Fix: also grep `JOIN nodes\b` and `JOIN edges\b`.
  2. **Multi-line template strings** where the `FROM nodes` keyword sits alone on its own line — the per-line grep matched the line but the predicate was inserted dynamically several lines below. Fix: P2.1.8 CI guard uses a 25-line context window.
  3. **Joined-table reads via comma** — e.g. `FROM edges, json_each(edges.provenances)` — same kind of multi-target SELECT as JOIN.
- The CI guard test (P2.1.8) ultimately caught all four missed categories at once. The audit-then-wire-then-test loop took 3 iterations; future P2 sub-tasks (P2.2/P2.3) should run the guard test EARLY (after writing any new prepared statement) rather than at the end.
- **The guard's regex evolution**: started as `\bFROM\s+(nodes|edges)\b` per-line. Had to add: (a) skip DELETE/INSERT/UPDATE multi-line statements via lookback, (b) skip ALTER TABLE / CREATE INDEX, (c) skip the helper's own subquery body. Each addition came from a real false positive in the first 2-3 runs. The final regex is conservative enough to be useful and lenient enough to not block legitimate writes.

## Risk callouts

- **`getStats` behavior change** is the largest user-visible diff (Decision 5). CHANGELOG must call it out. Existing tests that compare `getStats()` against a known total will need to either be updated to reflect the new semantics or switched to `getStatsIncludingStale()` for the comparison.
- **`searchNodesFuzzy` candidate cap** (line 705, `FUZZY_FOLLOWUP_CAP = max(limit*2, 50)`) is unchanged — but the candidate set is now filtered. On a fresh-after-refresh DB the behavior is identical; with hidden-stale rows the candidate set is smaller, which is the intended behavior.
- **`QueryGraphView` edge reads** flow through `QueryBuilder.getOutgoingEdges` / `getIncomingEdges` — they inherit the visibility-coherent default. Phase 3 augmenters see a coherent graph. (Decision 7 "Coherence inside Phase 3" confirmed.)
