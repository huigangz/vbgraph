# P1.5 PR-9 — rails migration

**Status**: complete
**Date**: 2026-05-23

## What landed

`src/resolution/frameworks/ruby.ts` rewritten.

- `detect` — unchanged.
- `extract` → `synthesize`:
  - Same routes.rb regex (`get/post/put/patch/delete/match '/x', to: 'c#a'`
    and `'/x' => 'c#a'`).
  - Emits one `route` node per match, ID prefix
    `framework:rails:route:<file>:<line>:<METHOD>:<path>`,
    provenance `framework:rails`.
- `resolve` dropped. The legacy suffix-based by-name lookups
  (`*Model` / `*Controller` / `*Helper` / `*Service` / `*Job`) used Rails
  naming conventions to map CamelCase → snake_case file paths. P0.5b's
  scope resolver doesn't cover Ruby (csharp/vbnet/java/python/typescript
  only), so we are losing some recall here. The migration trade-off is
  documented as "framework conventional lookup is best-effort heuristic"
  and is left to the import resolver / future enhancements.
- `augment` omitted (same as Python).

## Tests

- 2 `railsResolver.extract` tests rewritten to `synthesize` with
  `makeStubGraphView`. Drop the `references` assertions; assert route
  shape + provenance.
- 1 strip-comments regression rewired to `synthesize`.

All 63 tests across `frameworks.test.ts` + `p1-phase3-orchestrator.test.ts` pass.

## Notes

- The Ruby ecosystem currently has no scope resolver in P0.5b, so the
  resolve drop is a genuine recall regression for Rails projects.
  Acceptable trade-off per the plan's per-resolver migration guidance;
  the right fix is to extend the scope resolver to ruby (P3 work) rather
  than perpetuate the brittle Rails convention regex.
