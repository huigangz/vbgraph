# P1.5 PR-3 — aspnet migration

**Status**: complete
**Date**: 2026-05-23
**Plan**: [codegraph-framework-synthesize-augment.md § P1.5 — aspnet](../codegraph-framework-synthesize-augment.md)

## What landed

Edited `src/resolution/frameworks/csharp.ts` end-to-end. The
`aspnetResolver` is now a Phase 3 shape:

- `detect` — unchanged.
- `extract` → `synthesize(graph)`:
  - Iterates `graph.getAllFiles()` and skips non-`.cs` files.
  - Reads stripped content via `graph.readFileStripped(file, 'csharp')`.
  - Same attribute-route regex (`[HttpGet("/x")]` and friends) and same
    minimal-API regex (`.MapGet("/x", handler)`) as the legacy `extract`.
  - Emits one `route` node per match, IDs namespaced
    `framework:aspnet:route:<method>:<routePath>:<file>:<line>` (deterministic
    — re-running yields the same ID).
  - All emitted nodes carry `provenance = 'framework:aspnet'`.
  - No edges, no tags — those move to augment.
- `resolve` → `augment(graph)`:
  - Walks every node with `kind='route'` and `provenance='framework:aspnet'`.
  - `findHandlerName(graph, route)` recovers the handler ident:
    - Same-line minimal-API form: trailing ident from `.MapXxx("/x", handler)`.
    - Attribute form: walks up to 10 lines forward looking for the next
      `(public|private|protected|internal) ReturnType Name(` declaration.
  - Looks up `getNodesByName(handlerName)` filtered to method/function kind,
    prefers candidates in a Controllers/ directory, then falls back to
    a unique same-file collocation. Emits exactly one
    `references / convention` edge per matched route+handler pair (no
    metadata, NULL line/col per the allowlist).
  - Emits inherent tags `aspnet:controller` and `route-handler` on the
    handler node. Per the inherent-vs-derived contract: these are
    rule-based ("a method targeted by an aspnet route IS a route-handler"),
    so they go in `AugmentResult.tags` — they're derived from the edge
    construction this same augment is performing, so derived semantics
    fit. They become visible post-Phase-3.

The legacy by-name suffix / conventional-directory resolution (the old
`resolveByNameAndKind` flow for `*Controller` / `*Service` /
`*Repository` / `*Model` / `*ViewModel` / `*Dto`) is dropped entirely.
Per the plan: "largely subsumed by P0.5b's scope resolver for csharp" —
`frameworks.test.ts` covers shape, and no existing test depends on the
old `resolve` paths.

`extract` and `resolve` fields are GONE from the resolver. The legacy
hook block in `tree-sitter.ts` short-circuits via `if (!fw.extract)
continue`; the strategy-1 call in `resolution/index.ts` short-circuits
via `if (!framework.resolve) continue`.

## Tests

Updated `__tests__/frameworks.test.ts`:

- New helper `makeStubGraphView(files, language, options?)` (top of the
  file) — in-memory `GraphView` for testing migrated resolvers'
  `synthesize` / `augment` hooks without standing up a SQLite DB.
- `aspnetResolver.extract` test rewritten as `aspnetResolver.synthesize`
  — same source string, asserts shape (name, kind, provenance, ID
  prefix). Catches the "synthesized node provenance + ID prefix"
  invariant in addition to the shape the legacy test caught.
- The commented-out-route regression test (`aspnet: skips // and /* */
  commented [HttpGet] attributes`) was rewired to drive `synthesize` via
  the same helper. Strip-comments behavior is unchanged from the legacy
  path because both paths route through `stripCommentsForRegex`.

All 44 tests in `frameworks.test.ts` pass. The full PR-1 + PR-2 +
aspnet-migration suite (71 tests across 4 files) is green.

## Deferred

  covered by `upsertGraphEdge`'s existing P0.4 logic; an aspnet-specific
  regression adds little. Lands as a single cross-cutting test when
  multiple resolvers are migrated.
- **No frameworks-integration regression**: `frameworks-integration.test.ts`
  passes unchanged. It exercises the full extraction pipeline against
  Python/Rails fixtures, not aspnet — no aspnet-specific integration
  coverage exists in the repo.

## Notes for follow-up

- Augment is conservative: it only emits an edge when there's exactly
  one method candidate (or a unique same-file match). Multi-target
  ambiguity yields no edge rather than a wrong one — same precision/recall
  trade-off the plan describes for Temporal dispatch.
- The handler-search line window (10 lines) is heuristic. A future
  refinement could walk the AST instead of regex-scanning, but tree-sitter
  for csharp is Tier-0 and the line-walk is good enough for the
  attribute-then-method idiom.
- Once SCIP coverage is present for the same edge, `upsertGraphEdge`
  will merge: the aspnet augment becomes the `references/convention`
  contributor; SCIP's `calls` edge is independent at a different
  fingerprint and stays separate.
