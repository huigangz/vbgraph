# P2.6.1 — Perf regression for Decision 7's visibleNodeIdPredicate

**Status**: complete — **2/2 passing**.
**Date**: 2026-05-24
**Design commitment**: [P2.0-design.md](../P2.0-design.md) Decision 7 — "perf regression test with N=5000 hidden nodes; if it exceeds 200ms per edge query, escalate to a materialized hidden-id temp table per transaction".

## Test file

`__tests__/p26-perf-edge-visibility.test.ts` — standalone (not bundled with semantic tests) so timing assertions don't get flaky from shared-worker contention.

## What it asserts

| Operation | Threshold (native) | Threshold (WASM) | Setup |
|---|---|---|---|
| `getOutgoingEdges('source')` | 200ms | 1500ms | 5000 nodes marked hidden-stale across 1000 files, plus one fresh source→target edge |
| `getStaleSummary()` | 200ms | 1500ms | Same setup |

Both warm with one untimed call then average 10 timed calls. Threshold per-call.

## Measured results on this machine (WASM backend)

```
P2.6.1 perf: backend=wasm per-call=6.5ms (threshold=1500ms, 5000 hidden)
P2.6.1 perf: backend=wasm getStaleSummary per-call=2.5ms (threshold=1500ms)
```

Native would be ~5-10x faster — well below the 200ms native budget. **Design commitment satisfied with substantial headroom.** No materialization optimization needed.

## Why the partial index makes this cheap

[P2.1.1's partial index](../../../src/db/migrations.ts) `idx_nodes_stale ON nodes(stale) WHERE stale = 1` only contains hidden-stale rows. The `visibleNodeIdPredicate`'s subquery:

```sql
NOT IN (SELECT id FROM nodes WHERE stale = 1 AND staleness_visible = 0)
```

uses this partial index — the scan is exactly proportional to `|hidden|`, not `|all rows|`. With 5000 hidden + 5002 visible, scan cost is `O(5000)` not `O(10002)`. And `NOT IN` is well-optimized; the planner doesn't re-scan per outer row.

## WASM vs native thresholds

The convention in `foundation.test.ts` is to apply ~7x larger budgets on the WASM backend (5-10x is the documented slowdown ratio). P2.6.1 uses 1500ms / 200ms — same pattern. If a future contributor wants to enforce the strict 200ms on WASM, they can; nothing in the test prevents it. The looser WASM budget is for CI environments that have no native sqlite.

## What surfaces if this regresses

- **Removing the partial index** would drop WASM to seconds. Test would fail with a clear `per-call=Xms (threshold=Yms)` log line.
- **Inlining the hidden-set as a literal `NOT IN (id1, id2, …, idN)` clause** would be quadratic. Test catches it.
- **Materializing the hidden set per query without the index** would be linear-but-large. Test catches it.

## Risk callouts

- **CI runner variance** — slow shared runners may flake. Mitigation: thresholds are conservative (230x headroom on WASM today). If it does flake, raise the WASM threshold to 3000ms before assuming a real regression.
- **Setup time dominates wall clock** — 5000 inserts + 5000 stale marks take longer than the timed portion. That's expected; the test measures the QUERY cost, not setup.
- **Empty hidden set case** — not tested here. Common case; should be even faster. Covered implicitly by the existing test suites that all run with hidden=0.
