# P2.1.3 — `stale?: boolean` on Node/Edge + `rowToNode`/`rowToEdge` derivation

**Status**: complete
**Date**: 2026-05-24
**Decisions**: Design doc Decision 5 (visible-only public boolean; raw columns reserved for status/diagnostics).

## Changes

### `src/types.ts`

- Added `stale?: boolean` field to `Node` interface (line 191-ish, between `scipIndexPath` and `updatedAt`).
- Added `stale?: boolean` field to `Edge` interface (after `subkind`).
- Both fields documented with the exact derivation rule and the "visible-only" contract.

### `src/db/queries.ts`

- Extended `NodeRow` with `stale: number; staleness_visible: number;` (default 0, populated by SCIP/tree-sitter inserts in P2.1.4).
- Extended `EdgeRow` with the same two columns.
- `rowToNode` and `rowToEdge` now derive `stale: row.stale === 1 && row.staleness_visible === 1 ? true : undefined`.

## Why `undefined` for fresh rows (not `false`)

- Reduces JSON / MCP payload size by omitting the field on every fresh row (the common case).
- `stale === true` is the only assertion downstream consumers should make; `stale === false` is structurally identical to "absent" and gives no extra information.
- Mirrors the convention already used for `Node.visibility`, `Node.isExported`, etc. — fields that are absent when not meaningful.

## Why one boolean, not two

- Considered: separate `stale: boolean` and `staleness_visible: boolean` mirroring the schema columns. Rejected because hidden-stale never reaches the API (default predicate filters it out), so the API only needs to distinguish "fresh" vs "visible-stale" — one boolean suffices.
- Diagnostic surfaces (status command, parity, P2.4) read raw columns directly via `*IncludingStale` queries — they bypass `rowToNode` / `rowToEdge`.

## Test impact (deferred to P2.1.9)

- The derivation should be a no-op for the entire existing test corpus — every row written today has `stale=0`, so `rowToNode` / `rowToEdge` return `stale: undefined` and the field is omitted. Existing snapshot tests should remain stable.
- The P2.6 test sweep adds explicit visible-stale derivation tests.

## Risk callouts

- **Schema-driven typing drift**: `NodeRow` / `EdgeRow` are hand-typed mirrors of the SQLite columns. Adding columns without updating the row interface silently breaks `rowToNode` derivation. Mitigation: existing tests would fail at the type level if the DB returns extra fields, but no explicit "schema columns match interface" test exists. Worth a P3 cleanup pass.
- **`row.stale === 1` vs `row.stale === true`**: SQLite returns `INTEGER` columns as JS `number`, so `=== 1` is the correct check. better-sqlite3 and node-sqlite3-wasm both honor this. If a future adapter normalizes booleans, the derivation will need updating — but that's not the current state.
