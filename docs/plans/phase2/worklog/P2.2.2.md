# P2.2.2 — `deleteFileTreeSitterRows(file)` with `LIKE 'tree-sitter%'` predicate

**Status**: complete
**Date**: 2026-05-24
**Decisions**: design doc Decision 1 (provenance-scoped delete with `LIKE 'tree-sitter%'`, covers both shadow variants).

## Changes (`src/db/queries.ts`)

### `QueryBuilder.deleteFileTreeSitterRows(filePath)`

Two-stage delete inside one method:

1. **Edges** (deleted first, FK-ish ordering):
   ```sql
   DELETE FROM edges
     WHERE source IN (SELECT id FROM nodes WHERE file_path = ? AND provenance LIKE 'tree-sitter%')
        OR target IN (SELECT id FROM nodes WHERE file_path = ? AND provenance LIKE 'tree-sitter%')
   ```
   Symmetric source-OR-target — this is a hard delete, not staleness marking; the rows are owned by tree-sitter shadow and are being replaced wholesale. Different from `markScipFileStale`'s source-only edge marking, which serves the cross-file staleness lifecycle.

2. **Nodes**:
   ```sql
   DELETE FROM nodes WHERE file_path = ? AND provenance LIKE 'tree-sitter%'
   ```

Predicate `LIKE 'tree-sitter%'` catches both:
- `'tree-sitter'` — sync's regular shadow output
- `'tree-sitter (scip-empty-fallback)'` — created by SCIP ingest when a doc has zero occurrences (round 4 finding 2 / round 2 finding 2)

### Cache invalidation

File-scoped, BEFORE the SQL writes — same pattern as `markScipFileStale` (P2.2.1).

### Prepared-statement slots

Already declared in `stmts` during P2.2.1: `deleteShadowEdgesByFile`, `deleteShadowNodesByFile`. Used here.

## Why source-OR-target for the delete (not source-only)

The source-only invariant from design Decision 2 governs **staleness marking** — an edge becomes stale when ITS source file drifts, because that's the file SCIP would re-extract.

`deleteFileTreeSitterRows` is a different operation: it removes ALL tree-sitter rows the file owns, so the upcoming shadow extraction can re-emit cleanly. A tree-sitter edge OUT of file F (`source IN F`) gets re-emitted by the new extraction. A tree-sitter edge INTO file F (`target IN F`, source elsewhere) was emitted by some OTHER file's extraction — but if file F's old node ids no longer exist (they're being deleted), the cross-file edge becomes orphaned.

Two options:
- **Source-only delete**: leaves cross-file tree-sitter edges with dangling targets. P2.1.6's `visibleNodeIdPredicate` would filter them out at read time (target id not in nodes table), but the row exists forever as garbage.
- **Source-OR-target delete**: cleans up cross-file edges that target this file. The cost is that the OTHER file's tree-sitter extraction needs to re-emit the edge next time IT syncs. But that other file already has its (stale) source node, so the edge was a heuristic guess based on name-matching — re-resolving on next sync of that other file produces a fresh equivalent.

Source-OR-target is the cleaner long-term shape. Documented in the method comment.

## CI guard impact

The inner `SELECT id FROM nodes` subqueries inside the edge DELETE statement initially triggered the P2.1.8 guard. The lookback regex was only 5 lines and the DELETE-to-inner-SELECT distance was 7 lines (multi-line `WHERE source IN (...) OR target IN (...)` format).

**Fix**: bumped the `isPartOfWrite` lookback from 5 to 12 lines. Rationale documented in the test file: still safely under the public-read pattern's "compose predicate ahead" distance (where the predicate appends within 1-2 lines of the FROM clause).

Test now passes: 3/3.

## Risk callouts

- **Symmetric delete may erase cross-file tree-sitter edges from other files**. Mitigation: those edges were heuristic resolutions in the first place; the next sync of the OTHER file re-emits them based on the now-corrected target file. The cost is a short window where some cross-file connections temporarily disappear — acceptable for a sync-time operation.
- **`LIKE 'tree-sitter%'` predicate** could match a hypothetical future provenance like `'tree-sitter-experimental'`. If such a provenance is added, it would be silently deleted by shadow sync. Mitigation: add the provenance to `GraphProvenance` type and review this predicate at the same time. No current provenance starts with `tree-sitter` other than the two intended.
- **No transaction wrapper** around the two DELETEs. If the edge delete succeeds and the node delete crashes, the DB has dangling stale-node rows with no edges. Acceptable because: (a) the caller (sync) is expected to wrap the whole shadow extraction in a transaction; (b) the failure mode produces orphaned NODES, not orphaned EDGES — nodes without incident edges are valid graph state. If this becomes a real risk, wrapping in `this.db.transaction(...)` is one line.
