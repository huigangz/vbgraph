**Status**: complete

**Plan**: [codegraph-framework-synthesize-augment.md § P1.2](../codegraph-framework-synthesize-augment.md)

## What landed

New file: `src/resolution/graph-view.ts` (~230 lines).

### Interface

`GraphView` exposes:

- Node lookups: `getNode`, `hasNode`, `getNodesByKind`,
  `getNodesByQualifiedName`, `getNodesByName`, `getNodesByLowerName`,
  `getNodesByFile`, `getNodesByTag` (new — backed by P1.1), `getAllNodes`
  (generator).
- Edge lookups: `getOutgoingEdges` / `getIncomingEdges`, both with an
  optional `kinds` filter.
- File-system context: `getAllFiles`, `fileExists`, `readFile`,
  `readFileStripped` (per-language comment stripping via P0's
  `strip-comments.ts`), `getProjectRoot`.

All array returns are `readonly`. In dev mode (`CODEGRAPH_DEV=1`) each
returned array is shallow-frozen to catch accidental mutation; production
skips the freeze for perf.

`getAllNodes` is a generator yielding from `QueryBuilder.getAllNodes()`.
Caveat: the current QueryBuilder implementation materializes the result
internally; the generator wrapper documents intent. A follow-up that adds
a true streaming `getAllNodesIterator` to QueryBuilder is left for when
a resolver actually needs it (per the plan's "deferred unless needed"
discipline).

### Implementation — `QueryGraphView`

Thin wrapper over `QueryBuilder` with per-instance LRU-shaped `Map`s for
every node-side lookup, plus outgoing / incoming edge caches keyed by
`nodeId + sorted-kinds`. File-system reads are cached too (raw and
stripped variants).

Per-instance is load-bearing: STAGE C constructs a fresh view to pick up
STAGE B's writes; if caches lived on QueryBuilder, the cross-stage flush
in `invalidatePhase3Caches()` would have to clear them too. Per-instance
caches naturally drop on view replacement.

The view does NOT mutate QueryBuilder's caches. Phase 3's between-stage
freshness depends on `QueryBuilder.invalidatePhase3Caches()` calls (added
in P1.1, invoked from P1.4's orchestrator).

### Constructor signature

```ts
new QueryGraphView(queries, projectRoot, {
  exists(path: string): boolean,
  readFile(path: string): string | null,
})
```

The filesystem closure is injected rather than calling `node:fs`
directly. This matches `ResolutionContext.createContext` shape, lets
test code substitute an in-memory FS, and keeps `graph-view.ts` free of
`fs`/`path` imports.

## Notes for follow-up

- The view is unused until `Phase3Orchestrator` constructs it in P1.4.
- Cache invalidation only matters when the same view instance is used
  across writes — which Phase 3 forbids. STAGE C replaces the view, so
  per-instance caches stay coherent.
- If a resolver in P1.5 needs `getAllNodes` to truly stream from disk
  (no full materialization), revisit `QueryBuilder.getAllNodes` to add an
  iterator helper backed by `db.prepare(...).iterate()`.
