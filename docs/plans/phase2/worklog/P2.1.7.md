# P2.1.7 — `getStats` filter + `getStatsIncludingStale` + `getStaleSummary`

**Status**: complete
**Date**: 2026-05-24
**Decisions**: Design doc Decision 5 — three-surface model. `getStats` is the public/agent default (filter applied); `getStatsIncludingStale` is the raw escape hatch; `getStaleSummary` decomposes.

## Changes

### `src/types.ts`

Added `StaleSummary` interface:

```ts
interface StaleSummary {
  hiddenStale: { nodes: number; edges: number; files: number };
  visibleStale: { nodes: number; edges: number; files: number };
  fresh: { nodes: number; edges: number };
}
```

`files` counts distinct `file_path` values among NODE rows in the category (edges have no file_path).

### `src/db/queries.ts`

Three public methods (was one):

| Method | Behavior |
|---|---|
| `getStats()` | NOW applies `freshPredicate()` to node aggregates AND `freshPredicate + visibleNodeIdPredicate` to edge aggregates. Hidden-stale rows and edges with hidden endpoints are excluded. **Behavior change** vs P0/P1. |
| `getStatsIncludingStale()` | NEW. Raw `COUNT(*)`, no filter. For status diagnostics and parity. |
| `getStaleSummary()` | NEW. Reads raw `stale`/`staleness_visible` columns via composite `SUM(CASE …)` query — one round-trip for nodes, one for edges. Returns hidden/visible/fresh breakdown. |

The two public stats methods share a `computeStats({ applyFreshFilter })` private helper so the SQL composition stays in one place.

### Import addition

`StaleSummary` added to the `../types` import block in `queries.ts`.

## Edge stats use visibility-coherent count

`getStats().edgeCount` now matches "what `getOutgoingEdges` / `getIncomingEdges` would return totalled over all sources". Without the endpoint predicates, the count would over-report (dangling edges that no public read returns). This is the intended P2 semantic: count what consumers see.

`getStatsIncludingStale().edgeCount` reports the raw row count regardless of endpoint visibility — for parity and diagnostics.

## `getStaleSummary` SQL pattern

Used composite `SUM(CASE WHEN … THEN 1 ELSE 0 END)` in a single SELECT instead of three separate COUNTs:
- One scan of `nodes`, one of `edges` — half the I/O of the alternative.
- SQLite's optimizer rewrites `SUM(CASE)` over a full-table scan efficiently; on a fresh-after-refresh DB (hidden + visible-stale = 0), partial index `idx_nodes_stale WHERE stale = 1` cuts the stale-row scan to near-zero.
- `(SELECT COUNT(DISTINCT file_path) FROM nodes WHERE …)` for the `files` counters is two extra targeted lookups — each uses the partial index.
- SQLite returns `NULL` for `SUM` over zero rows; normalized via `nz(v) = v ?? 0`.

## Behavior-change CHANGELOG note (deferred to P2.6 CHANGELOG drafting)

`getStats()` exclusions:
- Hidden-stale nodes (`stale=1, staleness_visible=0`) — were counted before P2.1, no longer counted.
- Edges with hidden-stale endpoints — were counted before P2.1, no longer counted.
- Visible-stale rows are STILL counted (they pass the default filter).

Consumers depending on raw totals MUST switch to `getStatsIncludingStale()`. The most likely affected callers are `codegraph status` (already migrating to the three-surface model in P2.4) and any external programmatic users.

## Risk callouts

- **Test impact**: `__tests__/foundation.test.ts` and any test that calls `getStats()` and asserts exact totals will be unaffected ONLY IF the test fixtures never set `stale=1`. None do — the only stale-aware tests land in P2.6.
- **Composite SUM(CASE) query on large tables**: full-table scan in the worst case. On a fresh DB (the common state) `stale=0` for every row, and the scan is the same cost as the prior single COUNT. If a future codebase has tens of millions of stale rows AND `getStaleSummary` is called frequently, the cost could matter — but `getStaleSummary` is a status-only call, expected to run on-demand at human cadence.
- **Distinct-file-path subqueries**: when hidden/visible-stale counts are zero, these return 0 from a fast partial-index scan. When non-zero, they DISTINCT over the small hidden/visible subset — fast.
- **No `*IncludingDanglingEndpoints` for stats**: didn't add `getStatsExcludingDangling` or similar variations. The two surfaces (filtered vs raw) are enough for the design's use cases. If a future caller needs a third combination, add it then.
