# P1.5 PR-14 — Spring split + DI dispatch

**Status**: complete
**Date**: 2026-05-23

The load-bearing payoff PR of the plan. Replaces the monolithic
`springResolver` (formerly in `java.ts`) with two focused resolvers
and adds DI dispatch via `references/di_binding` edges.

## What landed

### New file: `src/resolution/frameworks/spring-core.ts`

- `name: 'spring-core'`, `languages: ['java']`.
- `detect` — same logic as legacy springResolver, extracted to a shared
  helper `detectSpring(context)` (also used by `spring-temporal`).
- `synthesize`:
  - **Bean inherent tags** on existing class nodes: walks
    `graph.getNodesByKind('class')`, reads annotations above each class
    declaration via `readClassAnnotations`, and emits one of
    `spring:service` / `spring:component` / `spring:repository` /
    `spring:configuration` / `spring:controller` per annotation. Per the
    plan's contract (R3-F1, R6-F1): bean tags MUST come from synthesize
    so they're persisted in STAGE B and visible to every augment via
    view2 — `isInjectionConstructor` reads them via `getNodesByTag`.
  - `@RequestMapping`-family `route` nodes — same regex as legacy
    `extract`, IDs namespaced `framework:spring-core:route:…`, provenance
    `framework:spring-core`.
- `augment` — three responsibilities:
  - **DI dispatch — field injection**: for each `kind='field'` java node
    with `@Autowired` or `@Inject` on the field line or two lines above,
    resolves the declared interface type (prefers `type_of` edge; falls
    back to regex on the declaration line) and emits one
    `references/di_binding` edge per implementing class.
  - **DI dispatch — constructor injection**: for each `kind='constructor'`,
    `isInjectionConstructor` returns true if (a) the ctor itself is
    `@Autowired`, OR (b) Spring 4.3+ implicit case — the enclosing class
    has a `spring:service`/`spring:component`/`spring:repository`/`spring:configuration`
    tag AND has exactly one constructor. For each qualifying ctor, walks
    its `contains` edges to find `kind='parameter'` children and emits
    di_binding from the parameter to every implementor of its declared type.
  - **Route → handler convention edges**: for each `framework:spring-core`
    route, walks 8 lines forward for the next public/private/protected
    method declaration, emits `references/convention` edge + `route-handler`
    tag, single-candidate-precision.
- All di_binding edges carry `kind='references'`, `subkind='di_binding'`,
  NULL line/col (permitted by `REFERENCES_SUBKINDS_ALLOWING_NULL_POSITION`),
  `provenance='framework:spring-core'`.
- Legacy by-name suffix lookups (`*Service` / `*Repository` / `*Controller`
  / entity PascalCase / `*Component` / `*Config`) dropped entirely —
  covered by P0.5b's Java scope resolver.

### New file: `src/resolution/frameworks/spring-temporal.ts`

- `name: 'spring-temporal'`, `languages: ['java']`.
- `detect` re-uses `detectSpring` from `./spring-core.ts` — Temporal is
  always wrapped in a Spring/Java app in this scope. The generic
  `temporal` resolver (PR-15) handles Java-without-Spring.
- `synthesize` — no-op.
- `augment`:
  - Pre-filters per file: skips java files that don't contain
    `newWorkflowStub` or `newActivityStub` substrings.
  - For each qualifying file, walks every `newWorkflowStub(X.class)` /
    `newActivityStub(X.class)` match. Same-line `.method(...)` call
    chain must follow. Strict matching: exactly one interface candidate
    AND exactly one implementor class via `implements` edges; the impl's
    same-named method must exist exactly once in the impl's file.
  - Computes the enclosing function/method/constructor by `startLine` /
    `endLine` range — that's the source for the dispatch edge.
  - Emits `kind='calls'`, `subkind='temporal_dispatch'`, line/col filled
    from the call site, `provenance='framework:spring-temporal'`.
- `seenSources` dedup ensures the same (enclosing, impl, line, col)
  doesn't produce duplicate edges.

### Registry changes (`src/resolution/frameworks/index.ts`)

- `springResolver` import + registration replaced with
  `springCoreResolver` + `springTemporalResolver`.
- `export { springResolver } from './java'` replaced with explicit
  exports for both new resolvers.

### Deleted: `src/resolution/frameworks/java.ts`

The monolithic file is gone. Its bean-detect logic moved to
`detectSpring` in `spring-core.ts`; route + DI logic to
`spring-core.ts`; nothing for Temporal in the legacy code (this PR
introduces it).

## Notes

- The DI test fixtures use stub GraphView nodes for `field`,
  `constructor`, `parameter` kinds. If tree-sitter's Java extractor
  doesn't emit those kinds today (some Tier-0 extractors omit them),
  the augment is correctly conservative: no parameter children → no
  di_binding edge. A separate enhancement to the Java extractor would
  light up the di_binding edges in real projects.
- `enclosingClass(graph, node)` walks `incoming(contains)` edges and
  picks the first `kind='class'` parent. Anonymous inner classes /
  nested types could fool this — acceptable approximation for now.
- Temporal dispatch's enclosing-function lookup uses node line ranges.
  If two methods share a line (one-liner), the deeper one wins via the
  `b.startLine - a.startLine` sort. Practical edge case; rare in Java.
- Both spring resolvers reuse `detectSpring` from spring-core. Detection
  is identical (Temporal apps are Spring apps in this scope), so both
  fire together on a Spring project.
