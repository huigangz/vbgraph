## Cache hit path safety

`getNodeById` checks `nodeCache` BEFORE running the prepared statement. The cached value bypasses the predicate. This is safe because:

1. Cache entries are populated from prepared-statement hits — so a cached row was visible at insert time.
2. P2.2's `markScipFileStale` / `deleteFileTreeSitterRows` invalidate the cache for affected `file_path` BEFORE mutating the row (per the Decision 1 cache invalidation rule).
3. P0.4d's `invalidatePhase3Caches` wholesale-clears the cache during raw-SQL purges.

Adding the predicate AFTER the cache check is therefore correct — a hit means the row was visible at cache-fill time AND has not been invalidated since.

## `*IncludingStale` siblings — deferred

The design doc allowed siblings for internal callers needing raw access. None of P2.2/P2.3/P2.4 require sibling methods:

- P2.2's `markScipFileStale` iterates `this.nodeCache` directly (no SQL read).
- P2.3's `countShadowRowsForFile` writes its own raw SQL (whitelisted).
- P2.4's status uses `getStats` / `getStatsIncludingStale` / `getStaleSummary` (P2.1.7).

So no `getNodeByIdIncludingStale` / `getNodesByFileIncludingStale` / etc. is added in P2.1. If a future caller needs one, adding it is a single-line method that wraps the raw SQL — the design's `*IncludingStale` naming convention is preserved by precedent.

The CI guard test (P2.1.8) will reject any future raw `SELECT … FROM nodes` outside the whitelist OR without `freshPredicate(`. Future contributors hit the test failure → either add the predicate or add a properly-named sibling on the whitelist.

## Risk callouts

- **Resolver paths (ResolutionContext)** rely on `getNodesByName` / `getNodesByQualifiedNameExact` / `getNodesByKind` / `getNodesByFile` / `getNodesByLowerName`. With the filter in place, resolvers now see only fresh+visible-stale nodes. Hidden-stale targets become unresolvable until refresh. This is the intended P2 contract — agents/augmenters reason over the visible graph. Tests under `__tests__/resolution.test.ts` may surface new "unresolved" cases if any rely on hidden-stale fixtures; none expected because the existing suite predates stale=1.
- **Search behavior**: `searchNodesFuzzy`'s candidate cap remains at `FUZZY_FOLLOWUP_CAP = max(limit*2, 50)`. With hidden-stale names excluded, the cap fills with relevant matches — round-5 finding 2's false-negative scenario closed.
- **FTS5 search** (main path at ~line 880, `FROM nodes_fts JOIN nodes ON …`) was MISSED by the inventory grep (which only matched `FROM nodes`, not the JOIN target). Caught and patched after the table was populated: `WHERE nodes_fts MATCH ? AND ${freshPredicate('nodes')}`. Hidden-stale FTS hits are now dropped at the join. The inventory has been corrected; future audits should also grep `JOIN nodes\b` / `JOIN edges\b`.
