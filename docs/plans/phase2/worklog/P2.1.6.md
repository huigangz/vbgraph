## SQL composition pattern

Multi-line backtick concatenation via `+`:

```ts
let sql = `SELECT * FROM edges WHERE source = ? AND ${freshPredicate()}`
  + ` AND source ${visibleNodeIdPredicate()}`
  + ` AND target ${visibleNodeIdPredicate()}`;
```

Chose this over template-literal-with-newlines to keep the resulting SQL on one logical line (better-sqlite3 happily handles either, but error messages quote the SQL verbatim — single-line is easier to read in failure logs).

## Performance: hidden-set scan cost

Both `source` and `target` independently invoke `NOT IN (SELECT id FROM nodes WHERE stale = 1 AND staleness_visible = 0)`. SQLite's planner sees the partial index `idx_nodes_stale WHERE stale = 1` (P2.1.1) and reuses the materialized result across the two `NOT IN` checks within one query — not two separate scans. Verified with EXPLAIN QUERY PLAN inspection on a sample DB during P2.1.6 development.

On the common case (zero hidden rows), the subquery returns an empty set and SQLite shortcuts the `NOT IN` to "always true" — effectively zero additional cost. Perf regression test at N=5000 hidden / 200ms is in P2.6.

## What graph/context layers see

- [`src/graph/queries.ts`](../../../src/graph/queries.ts) `getCallers`/`getCallees`/`getCallGraph` go through `QueryBuilder.getOutgoingEdges` / `getIncomingEdges`. They inherit the filter automatically.
- [`src/graph/traversal.ts`](../../../src/graph/traversal.ts) `bfs`/`dfs`/`findPaths`/`getImpactRadius` walk the graph via the same edge queries. Edges to hidden-stale endpoints are absent from the walk — the BFS frontier naturally terminates at the gap.
- [`src/resolution/graph-view.ts`](../../../src/resolution/graph-view.ts) `QueryGraphView.getOutgoingEdges`/`getIncomingEdges` (P1) delegate to QueryBuilder. Framework augmenters now reason over the visibility-coherent graph as the design doc Decision 7 promises.

## Risk callouts

- **Default visibility is now "coherent"** — a behavior change. Existing tests that expected dangling edges in result sets will break. The only stale-aware tests are net-new in P2.6; the existing test corpus uses `stale=0` everywhere, so no test should break from this wiring. P2.1.9 confirms.
- **`getOutgoingEdges(_, kinds=undefined, provenance=undefined)` and the fast-path prepared statement**: I patched BOTH branches (the kind-filter branch and the cached-prepared-statement bare branch). A skipped branch would silently re-introduce dangling edges. Spot-check: grep for `'SELECT * FROM edges WHERE source = ?'` post-edit returns matches that all include `freshPredicate(`.
- **The `*IncludingDanglingEndpoints` siblings** are deferred to where a real internal caller needs them (status command, parity diagnostic). Same pattern as P2.1.5's deferred `*IncludingStale` siblings.
