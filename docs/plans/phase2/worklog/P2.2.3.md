# P2.2.3 — `bulkMarkScipFilesStale(files[], visible)` with smart cache invalidation

**Status**: complete
**Date**: 2026-05-24
**Decisions**: design doc Decision 6 (branch-switch bulk path uses same `SCIP_FILE_PROVENANCES` predicate, file-scoped OR wholesale cache invalidation by size).

## Changes (`src/db/queries.ts`)

### `QueryBuilder.bulkMarkScipFilesStale(filePaths[], visible)`

Two UPDATE statements parameterized via JSON-each over `filePaths`, plus a smart cache invalidation strategy:

```ts
bulkMarkScipFilesStale(
  filePaths: readonly string[],
  visible: 0 | 1,
): { nodesMarked: number; edgesMarked: number; filesAffected: number };
```

### SQL design — `json_each` over JSON array

```sql
UPDATE nodes SET stale = 1, staleness_visible = ?
  WHERE file_path IN (SELECT value FROM json_each(?))
    AND provenance IN ('scip', 'tree-sitter (scip-empty-fallback)');

UPDATE edges SET stale = 1, staleness_visible = ?
  WHERE source IN (
    SELECT id FROM nodes
     WHERE file_path IN (SELECT value FROM json_each(?))
       AND provenance IN ('scip', 'tree-sitter (scip-empty-fallback)')
  );
```

Why JSON-each instead of `WHERE file_path IN (?, ?, ?, …)`:
- Variable-length `IN` clauses can't be cached as prepared statements — each batch size would need a new compile.
- `json_each` accepts a single string parameter regardless of batch size; one prepared statement serves all.
- SQLite's planner inlines `json_each` against the existing `idx_nodes_file_path` index — performance is equivalent to a static IN clause for batches under ~1000.
- Existing precedent: `findEdgesBetweenNodes` ([queries.ts:1307](../../../src/db/queries.ts#L1307)) uses the same JSON-each pattern.

Note: prepared statements NOT memoized in `this.stmts` — these are large-batch operations, expected to be called rarely (once per branch-switch sync). The .prepare() cost (~microseconds) is negligible compared to the UPDATE's row scan.

### Cache invalidation — size-aware

```ts
if (filePaths.length >= this.maxCacheSize) {
  this.nodeCache.clear();        // wholesale — file set is larger than cache
} else {
  const filePathSet = new Set(filePaths);
  for (const [id, node] of this.nodeCache) {
    if (filePathSet.has(node.filePath)) {
      this.nodeCache.delete(id);
    }
  }
}
```

Threshold rationale:
- `maxCacheSize` is 1000 ([queries.ts:258](../../../src/db/queries.ts#L258)).
- File-scoped invalidation is `O(cacheSize × O(1) Set.has)` = `O(cacheSize)`.
- Wholesale clear is `O(cacheSize)` constant-time-ish.
- At batch size ≥ cache size, the file-scoped loop is no cheaper (and the rebuild cost is the same), so wholesale wins on simplicity.
- For typical branch-switch batches (>50 but probably <500), the file-scoped path runs and preserves the cache of unaffected files.

Same `invalidate-before-mutation` ordering as `markScipFileStale` and `deleteFileTreeSitterRows` (round 4 finding 1).

## Return value

`{ nodesMarked, edgesMarked, filesAffected }` — `filesAffected = filePaths.length` is informational (matches the input cardinality, not the count of distinct files that actually had rows). Differs from `nodesMarked` / `edgesMarked` which are SQLite `changes` counts.

The sync caller (P2.2.4) uses `filesAffected` for the CLI warning ("Branch switch detected (N SCIP-covered files changed)").

## Risk callouts

- **JSON-each requires SQLite ≥ 3.7.5 (json1 extension)** — both backends (`better-sqlite3` native and `node-sqlite3-wasm`) ship with json1 enabled by default. No new compatibility concern.
- **Empty batch short-circuit**: returns zero-counts without touching the DB. Avoids running two no-op UPDATEs and the cache loop.
- **No transaction wrapper** — same rationale as `deleteFileTreeSitterRows`. The sync caller is expected to wrap. If a partial failure occurs (node UPDATE succeeds, edge UPDATE crashes), the DB has stale nodes but fresh edges — the freshness invariant is asymmetric but corrupts no data; the next sync would mark again and the edges would catch up.
- **Performance under very large batches**: JSON parsing scales with batch size. At 10,000+ files, the JSON string can hit MB range. Acceptable: branch switches in practice rarely exceed a few hundred files. If a real workload hits this, the threshold + batching is a P3 optimization.
