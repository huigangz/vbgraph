# P1.3 — `FrameworkResolver` interface extension

**Status**: complete
**Date**: 2026-05-23
**Plan**: [codegraph-framework-synthesize-augment.md § P1.3](../codegraph-framework-synthesize-augment.md)

## What landed

Edited `src/resolution/types.ts`:

- Imported `Edge`, `ExtractionError` from `../types`, plus `GraphView` from
  the sibling `./graph-view.ts`.
- `FrameworkResolver.resolve` is now optional (`resolve?`) and
  `@deprecated`. Migrating resolvers drop the field in their PR; the
  legacy strategy-1 call site short-circuits via a new guard.
- `FrameworkResolver.extract` is now `@deprecated`. Already optional in P0;
  no shape change, just a doc-comment marker.
- Added `FrameworkResolver.synthesize?(graph)` and `augment?(graph)`. Doc
  comments spell out:
  - The synthesize/augment ordering and view-rebuild guarantee.
  - Allowed node kinds for synthesis (`route`, `component` only — node-kind
    discipline).
  - Inherent vs derived tag semantics — inherent tags from synthesize are
    visible to all augments; derived tags from augment are not visible to
    sibling augments.
  - The "framework edges must not carry metadata" rule and why (metadata
    is owned by the static extractor, no retraction path otherwise).
  - The `framework:<name>` provenance suffix.
  - Per-resolver isolation: a thrown hook records one warning ExtractionError
    and quarantines that resolver's output.
- Added `SynthesizeResult` and `AugmentResult` types. Both carry optional
  `tags` and `errors`; SynthesizeResult.nodes is required and
  AugmentResult.edges is required.

Edited `src/resolution/index.ts:528`:

- Added `if (!framework.resolve) continue;` guard inside Strategy 1.
  Without this guard, `framework.resolve` being optional broke type
  checking against the iteration over `this.frameworks`. The guard also
  enables the gradual-migration story: each resolver migration PR drops
  its `resolve` field, the guard short-circuits, and the whole strategy
  is dead code by PR-15 / P3 cleanup.

## What did NOT change

- No existing resolver's behavior — all 16 resolvers still implement
  `resolve` and (where present) `extract`. They are unaffected.
- The legacy per-file `extract` block in `tree-sitter.ts:2550–2573` is
  untouched. It is removed in PR-16 after every resolver migrates.
- `ResolutionContext` is unchanged. `GraphView` is a strict superset, but
  retiring `ResolutionContext` is P3 work.

## Verification

- `npx tsc --noEmit` is clean.
- All existing resolvers continue to satisfy `FrameworkResolver`
  (verified by the clean type check — they implement `resolve` and the
  guard makes it optional, which is the only contract change).

## Notes for follow-up

- `synthesize` / `augment` are dead until P1.4's `Phase3Orchestrator`
  invokes them. Resolvers do not implement them yet.
- The doc comments on `synthesize` and `augment` are authoritative — when
  resolver migrations land in PR-3..15, their behavior must conform to
  the contracts described there. In particular: deterministic node IDs,
  the `framework:<name>` provenance prefix, no metadata on edges, and
  the inherent-vs-derived tag rule.
