# P2.1.4 — Node-write freshness clearing

**Status**: complete
**Date**: 2026-05-24
**Decisions**: Design doc Decision 3 (explicit `stale=0, staleness_visible=0` on every fresh node write — mirrors `upsertGraphEdge`'s freshness invariant from P0.4).

## Changes

### `src/db/queries.ts`

Three node-write prepared statements now explicitly name `stale` and `staleness_visible` in their column lists and write `0, 0`:

| Site | Statement type | Predicate semantics |
|---|---|---|
| `insertNode` (line ~285) | `INSERT OR REPLACE` | REPLACE clobbers the prior row; the explicit `0, 0` makes the freshness reset designed rather than accidental (default column value). |
| `insertNodeOrIgnore` (line ~1497) | `INSERT OR IGNORE` | IGNORE leaves an existing row untouched (correct for SCIP re-ingest where STAGE B has already scope-deleted prior rows). The explicit `0, 0` only takes effect on the new-row branch. |
| `updateNode` (line ~367) | `UPDATE` | Adds `stale = 0, staleness_visible = 0` to the SET list. Mirrors the freshness-clearing rule already used by `upsertGraphEdge` (see `queries.ts:1093`). |

### Why `insertNodes` is not separately touched

[`insertNodes`](../../../src/db/queries.ts) at line 350 is a thin batch wrapper that loops calling `insertNode`. Patching `insertNode` propagates automatically.

### Why `insertNodeOrIgnore` only conditionally clears

`OR IGNORE` skips the entire INSERT if the row exists — including any column re-writes. So a stale row that somehow survives to this code path stays stale until the caller explicitly handles it.

In the design, this case shouldn't happen: SCIP re-ingest is preceded by `deleteScipIndexData` (STAGE B) which removes prior SCIP rows for the index path before `insertScipNode` is called. The only path that could see a pre-existing stale row is external-symbol cross-index sharing (`upsertExternalScipNode`), and external nodes are never marked stale (they have no file_path that sync touches). So the conditional-clear semantics are correct.

If a defensive "always clear" path is ever needed, that's a P3 refactor — not in P2 scope.

## Validation

- Type-check + existing test suite at P2.1.9.
- Round-trip regression test in P2.6: insert a node, mark it stale via P2.2's helper, then call `insertNode` again with the same id (overlapping fingerprint via scope-resolution path) — assert the row clears back to `stale=0`.

## Risk callouts

- **Existing `insertNode` callers pass arbitrary `Node` objects**: the `0, 0` literals are hardcoded in the SQL, NOT taken from the `Node` parameter. So a caller cannot accidentally write `stale=1` via insertNode. This is the intended behavior — sync writes (markScipFileStale in P2.2) are the only path that sets stale=1.
- **`updateNode` may be called against SCIP nodes** that scope-resolution / framework augmenters target by id. The doc-comment already noted `updateNode` doesn't touch `provenance`; adding `stale` clearing is consistent — UPDATE means "this row is being freshly modified."
- **Prepared statement cache invalidation**: the SQL strings changed, so the `this.stmts.*` cached statements need to be re-prepared. Since the cache lives per-process and `init` runs `this.stmts = {}` implicitly (the field declaration `: {…} = {}`), this is fine for fresh processes. Existing long-running processes (the MCP server) would need to be restarted — but P2.1 is shipping with a schema migration, so a fresh-DB cycle is the expected path.
