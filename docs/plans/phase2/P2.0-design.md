The plan's P2 section was written assuming a stale-and-hide model that turns out to be incompatible with the current write paths. Five rounds of code review surfaced load-bearing mismatches (5 + 4 + 3 + 2 + 2); each round retracted or sharpened at least one claim from the previous draft. ## Background: node id derivation (load-bearing observation)

SCIP and tree-sitter produce structurally different ids for the same source-level concept:

| Source | id formula | Example |
|---|---|---|
| Tree-sitter | `${kind}:sha256(${filePath}:${kind}:${name}:${line})[0..32]` ([tree-sitter-helpers.ts:18](../../../src/extraction/tree-sitter-helpers.ts#L18)) | `method:a3f1...` for `MyClass.Foo` at `Foo.cs:42` |
| SCIP | `hashScipSymbol(scipSymbol)` ([scip/symbol-parser.ts](../../../src/extraction/scip/symbol-parser.ts)) | hash of `csharp scip-dotnet . MyClass#Foo().` |

**Consequence**: SCIP and tree-sitter rows for the same symbol are two separate rows in `nodes`, discriminated by `provenance`. This makes "coexist with one hidden" representable; "merge into one row" would not be (they have different ids). The whole stale-and-hide model rests on this fact.

Edges are merged across extractors via `upsertGraphEdge`'s fingerprint `(source, target, kind, subkind, line, col)` — but only when both extractors produce edges between the *same* node ids. Since tree-sitter and SCIP produce different node ids, tree-sitter-emitted edges almost never collide with SCIP edges on the fingerprint. The merge logic exists for the scope-resolved / framework augment paths (which DO target SCIP nodes by id when SCIP is present), not for shadow.

**This is the fact that round 2 finding 1 caught me misapplying**: when scip-refresh runs, the two coexisting rows do NOT merge via `pickPrimaryProvenance`. They are separate rows, and node queries like `getNodesByKind` return both. Refresh must explicitly purge shadow rows for files newly re-covered — see Decision 1.

## Decision 1 — Shadow write path preserves SCIP rows; refresh purges shadow rows

### Shared predicates (round 4 finding 2 + reuse)

Two named predicates underpin every SQL write in P2.2 / P2.3 / Decision 6. Both account for the dual-provenance "SCIP coverage of a file":

```ts
// SCIP-OWNED for a specific file path. Two provenance values qualify:
//   'scip'                              — SCIP-emitted node from a non-empty SCIP doc
//   'tree-sitter (scip-empty-fallback)' — SCIP-coverage-with-empty-doc fallback,
//                                         created at persister.ts:914 with the
//                                         SCIP doc's relativePath as file_path
// Excluded: 'scip:external' (symbol-level, file_path = '<external:...>')
const SCIP_FILE_PROVENANCES = ['scip', 'tree-sitter (scip-empty-fallback)'];

// TREE-SITTER-OWNED for a specific file path. One LIKE pattern covers both:
//   'tree-sitter'                        — sync's shadow output
//   'tree-sitter (scip-empty-fallback)'  — emitted by SCIP ingest when doc empty
// Used by deleteFileTreeSitterRows.
const TREE_SITTER_FILE_PROVENANCE_LIKE = 'tree-sitter%';
```

**Why the fallback shows up in both lists**: ownership cuts two ways. Semantically the fallback row is SCIP-coverage-with-empty-doc, so it MUST be marked stale when the SCIP source for the file drifts (Decision 1's mark, Decision 6's bulk mark). Mechanically the row's provenance starts with `tree-sitter`, so when scip-refresh restores SCIP precision it MUST be wiped along with the sync's shadow rows (Decision 1's delete). Both directions are correct — the row genuinely participates in both lifecycles.

### Cache invalidation rule (round 4 finding 1)

[`QueryBuilder` has an LRU `nodeCache`](../../../src/db/queries.ts#L168); [`getNodeById` reads cache before SQL](../../../src/db/queries.ts#L392). Any raw-SQL write that mutates `nodes` MUST invalidate cache entries for the affected rows, or queries observe stale-but-still-cached values. The pattern is already established:

- [`deleteNodesByFile`](../../../src/db/queries.ts#L381) — file-scoped invalidation (loops cache, drops entries with matching `filePath`)
- [`invalidatePhase3Caches`](../../../src/db/queries.ts#L1396) — wholesale flush, used by P1's STAGE 0 purge

P2's three new write helpers MUST invalidate inline:

| Helper | Invalidation |
|---|---|
| `markScipFileStale(filePath, visible)` | File-scoped — drop cache entries whose `node.filePath === filePath`. Same shape as `deleteNodesByFile`. |
| `deleteFileTreeSitterRows(filePath)` | File-scoped — same shape. |
| `bulkMarkScipFilesStale(filePaths[], visible)` (Decision 6) | If `filePaths.length` exceeds the cache size, wholesale `clearCache()`. Otherwise file-scoped loop (cheaper than rebuilding the warm cache). Threshold reused from `maxStaleFilesPerSync` (default 50). |

Regression test in P2.6: pre-warm cache via `getNodeById`, call helper, then call `getNodeById` again — assert the new state is observed (stale flag visible / row absent), not the cached pre-state.

### The mechanism

Split `deleteFile` into two operations:

```ts
// Existing — unchanged. Called by full-removal sync (file deleted from disk).
deleteFile(filePath: string): void                  // deletes ALL rows for file

// NEW — provenance-scoped via TREE_SITTER_FILE_PROVENANCE_LIKE.
// Invalidates nodeCache entries for this file before running the SQL DELETE.
deleteFileTreeSitterRows(filePath: string): void
```

Sync path becomes:

```
for each modified file F:
  if F in scip_documents:
    if isShadowCapable(language(F)):
      markScipFileStale(F, visible=0)               // marks SCIP rows stale (hidden)
      deleteFileTreeSitterRows(F)                   // remove any prior shadow rows
      treesitter_extract(F)                         // emit fresh shadow rows
    else:
      markScipFileStale(F, visible=1)               // marks SCIP rows stale-but-visible
      # no shadow extraction — no grammar available
  elif F not in scip_documents:
    # No SCIP coverage — full-replace behavior, unchanged from today
    deleteFile(F)
    treesitter_extract(F)
```

### What "fresh shadow rows" means in practice

After `treesitter_extract(F)`:

- **Nodes**: brand-new rows with `provenance='tree-sitter'`, ids derived from `filePath:kind:name:line`. They have no overlap with the (still-present, now-stale) SCIP nodes.
- **Edges**: the tree-sitter extractor emits edges via `upsertGraphEdge`. Most will be NEW rows (different source/target ids than the SCIP edges). Where fingerprints DO coincide (rare — would require a scope-resolved or framework edge whose endpoints are SCIP nodes), the existing freshness invariant at [queries.ts:1093](../../../src/db/queries.ts#L1093) handles it — `stale=0` reset on the merged row, primary `provenance` recomputed.

### Refresh: what happens to shadow rows (round 2 finding 1 — corrected)

When `codegraph scip-refresh` later runs, P0's ingester already handles shadow cleanup via two cooperating mechanisms:

1. **[persister.ts:594 STAGE E `supersedeTreeSitter`](../../../src/extraction/scip/persister.ts#L594)** — per-doc, deletes `provenance='tree-sitter'` rows for each `doc.relativePath` being processed. Catches the shadow rows that sync inserted between refreshes.
2. **[queries.ts:1520 STAGE B compatibility pass](../../../src/db/queries.ts#L1520)** — deletes `provenance='tree-sitter (scip-empty-fallback)'` rows for files in this `scip_index_path`'s `scip_documents`.

**P2 contribution**: broaden `supersedeTreeSitter`'s predicate from `provenance='tree-sitter'` to `provenance LIKE 'tree-sitter%'`. This unifies the cleanup so STAGE E alone catches both shadow row variants for the doc being processed — STAGE B's compatibility pass becomes a defense-in-depth duplicate rather than the sole guarantee for fallback rows. One-line change in `persister.ts`.

### Refresh post-ingest assertion — narrow scope (round 3 finding 1 — corrected)

**Important**: STAGE E intentionally creates **fresh** `'tree-sitter (scip-empty-fallback)'` rows AFTER `supersedeTreeSitter` runs, for docs whose SCIP occurrence count is 0 and whose file size exceeds the empty-fallback threshold ([persister.ts:646 maybeEmptyFallback](../../../src/extraction/scip/persister.ts#L646)). A blanket "no `tree-sitter%` row remains" assertion would fail on every empty-SCIP-document file.

The assertion must target sync's shadow rows specifically, NOT freshly-created fallback rows:

```ts
// P2.3 — scip-refresh post-ingest assertion (narrow).
//
// Target: rows whose provenance is exactly 'tree-sitter' (sync's shadow output).
// Excluded: 'tree-sitter (scip-empty-fallback)' rows — these are legitimately
//           created by STAGE E for empty SCIP documents and are part of the
//           refreshed graph, not stale shadow leakage.
for (const filePath of refreshedScipDocuments) {
  const shadowCount = qb.countShadowRowsForFile(filePath);
  //   internally: SELECT COUNT(*) FROM nodes
  //               WHERE file_path = ? AND provenance = 'tree-sitter'
  assert(shadowCount === 0,
    `scip-refresh leaked ${shadowCount} shadow nodes for ${filePath}`);
}
```

The assertion catches: (a) `supersedeTreeSitter` not running for some doc (regression), (b) shadow rows inserted after STAGE E but before commit (impossible by current ordering, but the assertion guards against future restructuring).

### Why not "merge" via shared node id

Considered: rewrite SCIP and tree-sitter to produce the same id. Rejected:
- SCIP id derivation is property of the SCIP symbol string (cross-`.scip` compatibility, external-symbol cross-index sharing in `scip_external_refs`). Locked.
- Tree-sitter id derivation uses `(filePath, kind, name, line)` because tree-sitter has no symbol-resolution to produce a stable cross-file identifier.
- Unifying would require either tree-sitter doing symbol-resolution (= reinventing SCIP) or SCIP losing cross-index identity.

The two-row coexistence is correct; refresh's job is to delete the shadow row once SCIP precision is restored.

## Decision 2 — Source-only edge staleness

### The rule

When file X changes, mark edge E stale **only if `source(E)` is in X**. Do NOT mark when `target(E)` is in X.

### SQL

```sql
-- Node side (used by markScipFileStale)
UPDATE nodes SET stale=1, staleness_visible=?
 WHERE file_path=?
   AND provenance IN ('scip', 'tree-sitter (scip-empty-fallback)');
-- (Above predicate = SCIP_FILE_PROVENANCES — see Decision 1 shared predicates.
--  Excludes 'scip:external' because those have synthetic file paths.)

-- Edge side (source-only — see "Why" below)
UPDATE edges SET stale=1, staleness_visible=?
 WHERE source IN (
         SELECT id FROM nodes
          WHERE file_path=?
            AND provenance IN ('scip', 'tree-sitter (scip-empty-fallback)')
       );
-- The inner SELECT uses SCIP_FILE_PROVENANCES, NOT 'LIKE scip%'.
-- An edge sourced from a fallback row participates in the same staleness
-- lifecycle as its source node.
```

### Why

1. **Single row-level flag is enough.** `upsertGraphEdge`'s `stale=0` reset is unconditional; if both source-X and target-Y can mark the same row stale at different times, the first one to re-extract clears the flag — losing the other side's stale signal.
2. **Matches SCIP indexer semantics.** A SCIP indexer's incremental output for changed file X regenerates edges *sourced from X*. Edges sourced from Y that happen to target a symbol in X don't get re-emitted — they're not in scope.
3. **Target-side drift is handled by fingerprint change.** If target-side identity actually changes (function renamed, signature changed), the edge fingerprint `(source, target, …)` no longer matches; the old edge row orphans and the new one inserts. No stale tracking needed.
4. **No schema change.** The plan's symmetric model with independent clearing would require splitting into `stale_source` / `stale_target` columns. Source-only stays at one column.

### What this gives up

- **Soft signal that "this edge points into a file that has drifted since last refresh"** — lost. If you care: the public `stale?: boolean` (Decision 5) plus a post-query check `targetFileChangedSince(edge, lastRefresh)` can synthesize the signal at status-command time without a column.
- **Edge appears fresh when target node is hidden-stale.** This was the visibility gap round 5 caught. **Decision 7** closes it by filtering edges at query time on endpoint visibility. The edge's `stale` flag stays source-side per this Decision; the visibility consistency comes from the query-layer predicate, not from an additional column.

### Plan section to retract

The "**Edge case — symmetric endpoint test**" paragraph at plan line 1469 and its regression test. Replaced by a source-only regression in P2.6.

## Decision 3 — Explicit node freshness clearing

### The change

`insertNode` ([queries.ts:222](../../../src/db/queries.ts#L222)) adds `stale` and `staleness_visible` to the column list and writes `0` explicitly:

```sql
INSERT OR REPLACE INTO nodes (
  …existing columns…,
  stale, staleness_visible                                   -- NEW
) VALUES (
  …existing values…,
  0, 0                                                       -- NEW
)
```

Mirrors `upsertGraphEdge`'s "fresh contribution = fresh row" invariant. Removes the dependence on column DEFAULT 0 (which only saves us today by accident).

### Why this matters even with Decision 1

Decision 1 means tree-sitter shadow inserts have different ids from the SCIP rows, so `INSERT OR REPLACE` on a shadow row never touches a SCIP row's `stale=1` flag. So in theory the SCIP rows stay stale-and-hidden until refresh, regardless of what `insertNode` does.

But: scope-resolved nodes and framework synthesized nodes CAN target SCIP node ids (P0.5b scope resolver writes refs against SCIP nodes when SCIP is present; framework augmenters write tags against SCIP nodes). If a later re-resolve / re-augment pass writes to a SCIP node id via `INSERT OR REPLACE`, we want the freshness invariant to fire. Explicit `0, 0` makes it deterministic.

### Audit gate

Every node-write path needs to be uniform on this. P2.1 checks: `insertNode`, `insertNodes` (batch), `insertScipNode` (P0.4 added this — needs the same treatment), `updateNode`.

## Decision 4 — Centralized freshness filter helper

### The mechanism (round 3 finding 2 — corrected)

The first draft proposed `withFreshnessFilter(sql)` that **appends `AND (…)`** to existing SQL. That breaks for clauseless statements — `getAllNodes()`'s `SELECT * FROM nodes` ([queries.ts:464](../../../src/db/queries.ts#L464)) has no `WHERE`, so appending `AND (…)` produces invalid SQL.

Adopted: a **predicate-only helper** with no clause assumptions. Callers compose explicitly:

```ts
// src/db/queries.ts — single export, no clause keywords.
export function freshPredicate(alias: string = ''): string {
  const a = alias ? alias.endsWith('.') ? alias : `${alias}.` : '';
  return `(${a}stale = 0 OR ${a}staleness_visible = 1)`;
}

// Callers compose with WHERE or AND depending on context:
db.prepare(`SELECT * FROM nodes WHERE ${freshPredicate()}`);                  // clauseless
db.prepare(`SELECT * FROM nodes WHERE name = ? AND ${freshPredicate()}`);     // existing WHERE
db.prepare(`SELECT * FROM nodes n JOIN files f WHERE ${freshPredicate('n')}`); // joined
```

The helper returns the predicate only; the caller owns SQL composition. Always-safe at the cost of one extra word per call site.

### CI guard

A grep test (`__tests__/p21-no-bypass.test.ts`) asserts the conjunction of:
- Every prepared statement against `nodes` or `edges` either includes `freshPredicate(` or appears in the explicit `*IncludingStale` whitelist (defined in the test file as a list of method names + line ranges).
- No raw `SELECT … FROM nodes` / `SELECT … FROM edges` exists outside that allowlist.

Failure mode: a contributor adds `db.prepare('SELECT * FROM nodes WHERE foo = ?')` → CI fails with a pointer to the inventory checklist and `freshPredicate` docs.

### Inventory completeness

Every prepared statement that reads `nodes` or `edges` for public-facing data MUST use `freshPredicate`. `*IncludingStale` siblings exist for:

- `codegraph status` (must see hidden-stale to report them) — see Decision 5 update
- Parity harness (debugs all rows)
- Sync's own scoped reads (e.g., `markScipFileStale` looks at SCIP rows regardless of stale state)
- `scip-refresh`'s STAGE B (deletes by `scip_index_path` regardless of stale state)
- **`getStatsIncludingStale()` for status diagnostics** — see Decision 5

## Decision 5 — `stale?: boolean` on types (API surface) vs raw columns (internal)

### The change

Add ONE optional field to each of Node and Edge:

```ts
// src/types.ts
interface Node {
  // … existing fields …
  /** True iff this row is visible-but-stale (came from a stale SCIP shadow with no
   *  tree-sitter grammar available). Hidden-stale rows never reach the API. */
  stale?: boolean;
}

interface Edge {
  // … existing fields …
  /** Same semantics as Node.stale. */
  stale?: boolean;
}
```

Derived in `rowToNode` / `rowToEdge` from `row.stale === 1 && row.staleness_visible === 1`. Hidden-stale never reaches the API by Decision 4's default filter, so `stale === true` always means "visible, but flagged as fallback".

### What this enables (API surface)

- `codegraph context` and MCP tools can surface "⚠ stale fallback" annotations to AI agents.
- Agents can decide: ignore stale results, downweight them, or proceed with caution.

### `codegraph status` does NOT use this boolean (round 2 finding 3 — corrected)

The original draft said status "derives the count via `r.stale === true`". That was wrong: `r.stale === true` only covers visible-stale (`stale=1 AND staleness_visible=1`). Status needs to count **both** stale categories distinctly:

| Category | Raw column state | Public boolean | What status reports |
|---|---|---|---|
| **Hidden-stale** | `stale=1, staleness_visible=0` | (not exposed) | "Shadow active — tree-sitter is filling in for SCIP on these files; refresh when convenient" |
| **Visible-stale** | `stale=1, staleness_visible=1` | `stale: true` | "Needs refresh — no tree-sitter grammar; you're seeing SCIP data that may have drifted" |
| **Fresh** | `stale=0` | `stale: undefined` | (default) |

Status uses three cooperating QueryBuilder helpers (round 3 finding 3):

```ts
// 1. getStats() — APPLIES the freshness filter. Default contract.
//    Existing callers of CodeGraph.getStats() now see fresh+visible-stale only;
//    hidden-stale is excluded (matches Decision 4's default-query contract).
getStats(): GraphStats;

// 2. getStatsIncludingStale() — NEW. Raw COUNT(*) without filter.
//    For status diagnostics and parity checking.
getStatsIncludingStale(): GraphStats;

// 3. getStaleSummary() — NEW. Decomposes the stale state.
getStaleSummary(): {
  hiddenStale: { nodes: number; edges: number; files: number };
  visibleStale: { nodes: number; edges: number; files: number };
  fresh:        { nodes: number; edges: number };
};
```

`codegraph status` calls `getStats()` for the headline numbers (matching what AI agents see), `getStaleSummary()` for the per-category breakdown, and optionally `getStatsIncludingStale()` for an "X hidden behind shadow" totals line.

**Default-contract migration impact**: existing consumers of `CodeGraph.getStats()` will see counts that exclude hidden-stale nodes/edges. This is intentional — once shadow rows exist, the API's stats should match the API's queries. CHANGELOG calls this out as a behavior change for `getStats`; `getStatsIncludingStale` is the explicit escape hatch for callers who want the raw total.

The public `stale?: boolean` is for AI-agent-facing query results; the raw columns + `getStatsIncludingStale` + `getStaleSummary` are for status/diagnostics. They are intentionally separate surfaces.

### What this excludes

- Hidden-stale never reaches the API by Decision 4's default filter. The whole point of hiding is to keep it out of agent context.
- Internal sync code reads the columns directly via `*IncludingStale` queries; the API-level boolean is for downstream consumers only.

## Decision 6 — Branch-switch behavior (round 2 finding 4)

### The rule

When the sync sees `changedScipFiles > maxStaleFiles` (default 50, configurable via `CodeGraphConfig.maxStaleFilesPerSync`):

- **Mark all affected SCIP-owned rows with `staleness_visible=1`** (stale-but-visible), regardless of whether the file's language is shadow-capable.
  - **Predicate is `SCIP_FILE_PROVENANCES`** (Decision 1 shared predicates), NOT `LIKE 'scip%'`. Round 4 finding 2: the prior wording missed `'tree-sitter (scip-empty-fallback)'` rows. Same SQL shape as the per-file `markScipFileStale`, just batched over a path set.
- **Skip the per-file shadow extraction** (the whole point of the threshold).
- **Invalidate the node cache** via `bulkMarkScipFilesStale` (file-scoped loop, or wholesale `clearCache()` if the affected file count exceeds the cache size — see Decision 1 cache invalidation rule).
- **Emit one warning** to the CLI: `"Branch switch detected (N SCIP-covered files changed). Skipping per-file shadow; SCIP data may have drifted. Run 'codegraph scip-refresh' to restore precision."`
- **Status command** reports the bulk-stale count under "Needs refresh" (since `staleness_visible=1`).

### Why visible=1, not visible=0

- Branch switch is a high-frequency operation; the threshold exists because shadow extraction for >50 files would dominate sync time, not because the data has become dangerous.
- Marking with `staleness_visible=0` (hidden) would make whole files disappear from default queries — likely most of the codebase if the branch differs significantly. Tanks navigation utility for what may be a temporary side trip onto another branch.
- Marking with `staleness_visible=1` keeps the SCIP graph queryable with the API's `stale: true` annotation. AI agents and humans both get a "this might be stale" signal but can still navigate.
- Refresh closes the gap when the user chooses to spend the time.

### What this gives up

- **Cross-branch correctness when branches differ structurally**: a file renamed on the other branch will still resolve to the old name on this branch until refresh. Documented in CHANGELOG.

## Decision 7 — Edge endpoint visibility coherence (round 5 finding 1)

### The problem

Decision 2 marks edges stale only when **source file** changes. That's correct for the freshness lifecycle. But it creates a visibility gap when the **target file** changes:

```
File X (unchanged):     fresh SCIP edge   X.foo  ──calls──▶  Y.bar
File Y (just edited):   markScipFileStale → Y.bar's SCIP node becomes hidden-stale
                                                              ▲
                                                              │
Result: the edge row passes the edge-side freshness filter   │
        (its own stale=0); the target node row is hidden by  │
        the node-side filter. Public edge queries return the │
        edge; node lookups on its target return null.        │
        Consumers see a dangling reference. ─────────────────┘
```

The current edge queries return rows directly with no endpoint check ([queries.ts:1152 `getOutgoingEdges`](../../../src/db/queries.ts#L1152), [queries.ts:1181 `getIncomingEdges`](../../../src/db/queries.ts#L1181), etc.).

### The rule

**Public edge queries filter out edges whose source OR target is currently hidden-stale.** Filtering happens in SQL using the partial `idx_nodes_stale WHERE stale=1` index for fast lookup of the hidden set.

```ts
// New helper alongside freshPredicate.
// Returns: NOT IN (SELECT id FROM nodes WHERE stale=1 AND staleness_visible=0)
// Caller AND-s this against the relevant edge column (source or target).
export function visibleNodeIdPredicate(): string {
  return `NOT IN (SELECT id FROM nodes WHERE stale = 1 AND staleness_visible = 0)`;
}
```

Every public edge query composes:

```sql
SELECT * FROM edges
 WHERE source = ?
   AND ${freshPredicate()}                       -- edge's own staleness
   AND source ${visibleNodeIdPredicate()}        -- source not hidden
   AND target ${visibleNodeIdPredicate()};       -- target not hidden
```

### Why `NOT IN (hidden set)` and not a JOIN

- The hidden set is small in the common case (0 rows when freshly refreshed; tens to hundreds during normal editing).
- `idx_nodes_stale WHERE stale = 1` (partial index, P2.1) means the subquery is a near-empty index scan.
- `NOT IN` against an indexed subquery is well-optimized by SQLite's planner; no row multiplication.
- JOIN equivalents (`LEFT JOIN nodes n ON e.target = n.id WHERE n.stale = 0 …`) multiply work by edge count even when no hidden nodes exist.

### `*IncludingDanglingEndpoints` siblings

Parallel to Decision 4's `*IncludingStale` pattern. Internal consumers that DO want dangling-edge visibility:

- **Status command** — reports "N edges currently dangling against hidden-stale nodes" as part of the staleness diagnostics.
- **Parity harness** — debugs all rows.
- **Sync's own scoped reads** — `markScipFileStale`'s edge SQL uses raw access (per Decision 2).
- **Phase 3's GraphView** — open question, see "Coherence inside Phase 3" below.

API names: `getOutgoingEdgesIncludingDanglingEndpoints`, `getIncomingEdgesIncludingDanglingEndpoints`, etc. Long names are intentional friction; the default API stays terse.

### Coherence inside Phase 3 (resolved)

`QueryGraphView` reads edges during `augment()`. A framework augmenter reasoning over the graph should not see edges to hidden-stale nodes (those nodes are conceptually absent from the visible graph). Decision: **`QueryGraphView`'s edge reads go through the visibility-filtered API**. Same default contract as the public edge queries — agents/augmenters see a coherent graph.

The cost: when sync triggers Phase 3 unconditionally after extraction, and there are hidden-stale rows from the just-marked SCIP, the augmenters work against the post-shadow graph. That's the intended behavior (Phase 3 should reflect what queries return). If a future augmenter needs to see hidden rows, it can opt in via `*IncludingDanglingEndpoints`.

### CI guard extension

The CI bypass guard test (Decision 4) extends to assert every public edge query SQL string contains BOTH `freshPredicate(` AND `visibleNodeIdPredicate(` (or appears in the explicit `*IncludingDanglingEndpoints` whitelist).

### What this gives up

- **Edge counts in `getStats()` and other aggregates that scan `edges`**: edges-with-hidden-endpoints are excluded by the same predicate. `getStatsIncludingStale()` (Decision 5) reports the raw count. Status command shows both.
- **Speed when hidden set is large**: in pathological cases (large branch switch + bulk-mark, see Decision 6), the hidden set could be thousands of rows. The partial index still helps but the planner may scan it linearly. P2.6 includes a perf regression test with N=5000 hidden nodes; if it exceeds 200ms per edge query, escalate to a materialized hidden-id temp table per transaction. Defer the optimization unless the regression test fails.

## What this design explicitly does NOT promise

- **Tree-sitter shadow producing the same call/reference graph as SCIP did.** Shadow is heuristic. Edges sourced from F may differ between SCIP and tree-sitter; that's the cost of editing a SCIP-covered file between refreshes. Documented in the CHANGELOG entry.
- **Cross-file resolution under shadow.** Tree-sitter shadow runs through `ReferenceResolver` (P0.5b scope-resolved + heuristic), not SCIP precision. A shadow edge from F into a SCIP-covered file Y may bind incorrectly. Acceptable: refresh closes the gap.
- **Per-edge endpoint reason tracking.** Decision 2 explicitly drops this. If users report needing it, it becomes a P3 design conversation, not a P2 patch.
- **Real-time MCP staleness signals during a sync.** The sync transaction is brief; MCP queries during it block via SQLite's normal serialization. No mid-sync visibility.
- **Hidden-stale visibility in the public API.** Decision 5 keeps hidden-stale strictly internal (`getStaleSummary` for status only). If an agent ever needs to know about hidden-stale rows, that becomes a new explicit query (e.g., `getNodesIncludingHidden`), not a relaxation of the default filter.
- **Cross-branch correctness when many files differ.** Decision 6's bulk-mark surfaces drift via `stale: true` but does not fix it. Refresh is required.
- **Performance under pathological hidden-set sizes.** Decision 7's `NOT IN` subquery is well-indexed for the common case (hidden set < 100). For extreme branch switches or large monorepos with thousands of stale files between refreshes, the hidden-set scan may dominate edge query time. P2.6's perf regression test catches this at 5000 hidden nodes / 200ms threshold; exceeding it triggers an explicit materialization-temp-table follow-up (not in P2 scope).
